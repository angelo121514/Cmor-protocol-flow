### Reproducción, intentos y límites

Proyecto exclusivo `cmor-flow-open-source-validation`, API55421/DB55422, PostgreSQL17.6, CLI2.107.0, runtime Edge1.74.1 y SDK2.86.0 instalado. Se preservaron otros proyectos/contenedores/volúmenes. Las89 migraciones originales no se editaron;30 nuevas aplicadas en ambos caminos. El baseline se materializó con89 migraciones, se sembraron datos históricos, se aplicó el delta y se comprobaron los backfills. Clean no se usa como sustituto de upgrade.

Comandos: `node scripts/reset-local-validation.mjs --baseline`; `node scripts/prepare-upgrade-local.mjs`; `supabase migration up --local`; `EXPECT_UPGRADE_FIXTURE=1 npm run test:database`; luego reset sin --baseline, retirar EXPECT_UPGRADE_FIXTURE y repetir test:database. En PowerShell usar `$env:EXPECT_UPGRADE_FIXTURE='1'` y retirarlo con Remove-Item Env:EXPECT_UPGRADE_FIXTURE. Runner bloquea URL externa, proyecto incorrecto, fixtures ausentes y ejecuciones concurrentes; pgTAP usa psql del contenedor instalado. Espera el anuncio de su nueva instancia Edge antes de readiness; no relaja assertions ni acepta skips.

Se registraron y corrigieron intentos fallidos: inicialización Realtime/Storage, arranque Edge prematuro, fixtures reutilizados, etiquetas y limpieza FK, rol incorrecto en prueba de backfill y cancelación repetida real. Un proceso lint terminó anormalmente; sólo la repetición exitosa cuenta. El reset aísla Realtime y exige startup saludable, sin ignore-health-check. La primera invocación de supabase test db descargó automáticamente pg_prove:3.36; se sustituyó por ejecución offline sin helper. No se contactó ningún proveedor de negocio real.

Vitest mide sólo módulos importados/instrumentados. Las38 assertions SQL no se suman como38 tests de Vitest; las2 pruebas de upgrade no pertenecen a clean. Los6 públicos son simulados y los6 privados usan Auth/SQL reales. No se ejecutaron E2E históricos contra staging, scripts administrativos, backups/restauraciones de negocio, auditoría npm online ni CI remoto. Fixtures son datos desechables, no datos de producción. Logs/credenciales sintéticas permanecen ignorados; hashes/resultados resumidos en LOCAL_VALIDATION.json (referencia histórica excluida de esta distribución).

Requiere validación humana: catálogo/monedas/métodos y contratos reales, propietarios/grants/migraciones desplegados, cron/configuración/firmas, retención y baja contractual, zonas regionales, logs históricos, recovery MFA/outbox/DTE.
